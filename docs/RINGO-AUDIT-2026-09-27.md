# 링고 코드·기능·UI/UX 점검 보고서

점검일: 2026-09-27 · 대상: 로컬 `main` 작업 트리와 기존 미커밋 공유 카드 변경

**판정: 화면 구성과 기본 기능의 기반은 잘 갖춰져 있으나, 실결제 운영 전에 결제 상태 일관성·환불·쿠폰 동시 처리부터 보완해야 합니다.** 타입 검사, 린트, 배포용 빌드는 통과했습니다. 그러나 컴파일 성공과 별개로 업무 로직의 오류를 재현했습니다.

이번 작업은 점검과 보고입니다. 기존 서비스 코드는 수정하지 않았고, 재현용 코드는 `.data/audit-2026-09-27/`에 두었습니다. 결제·환불·정산 변경 테스트는 **별도의 메모리 DB**에서 실행했으며 실제 결제사 호출, 송금, 외부 메일 전송은 하지 않았습니다. 브라우저에서는 로컬 데모 계정 로그인과 화면 조회를 수행했습니다.

모든 화면의 모든 입력 조합을 실행한 것은 아닙니다. 운영 PostgreSQL 다중 인스턴스, 실제 PG·SMTP·S3, 실제 카카오톡 앱의 캐시 갱신까지 검증한 결과는 아닙니다. 동시성 문제는 임시 DB에서 두 요청을 병행하거나, 읽기와 쓰기 사이에 결제 완료가 도착하도록 실행 순서를 제어하여 재현했습니다.

## 2. 우선 수정할 기능 결함

P1은 금액·구매 권한·운영 기록에 영향을 주어 실결제 운영 전에 우선 해결할 항목입니다. P2는 기능 신뢰성과 사용성 개선을 위해 다음으로 수정할 항목입니다.

### 1) P1 — 동시 환불 요청이 결제사 환불을 두 번 호출할 수 있음

- **근거:** [commerce.ts:422](E:/프로젝트/링고/lib/server/commerce.ts:422), [commerce.ts:433](E:/프로젝트/링고/lib/server/commerce.ts:433)
- 환불 처리기를 먼저 호출하고, 그 뒤 DB에서 주문을 `paid → refunded`로 선점합니다. DB 중복 처리는 막지만 외부 환불 요청의 중복은 막지 못합니다.
- **재현:** 같은 주문을 두 요청에서 동시에 환불했습니다. 대체한 테스트 환불 처리기 호출은 **2회**, DB 성공 환불 기록은 **1건**, 나머지 요청은 `invalid_state`였습니다.
- **영향:** 실제 PG가 중복을 방지하지 않으면 중복 환불 요청이 나가거나, PG 결과와 내부 기록이 달라질 수 있습니다. 실제 중복 송금을 확인한 것은 아닙니다.
- **권장:** 외부 호출 전에 환불 작업을 원자적으로 선점하고, 주문/환불 단위의 고정 멱등 키를 PG에도 전달합니다. PG 성공 후 DB 기록 실패를 복구할 재처리 경로도 마련합니다.

### 2) P1 — 결제 성공과 취소·만료·실패가 겹치면 상태가 충돌함

- **근거:** [commerce.ts:274](E:/프로젝트/링고/lib/server/commerce.ts:274), [commerce.ts:309](E:/프로젝트/링고/lib/server/commerce.ts:309), [commerce.ts:340](E:/프로젝트/링고/lib/server/commerce.ts:340)
- 최초 조회에서는 미결제였더라도, 나중 UPDATE 시 현재 상태를 다시 조건으로 검사하지 않는 경로가 있습니다.
- **재현 결과:**
  - 취소 조회 직후 결제 완료 → 주문 `cancelled`, 결제 `succeeded`, 활성 구매 권한 1개.
  - 일괄 만료 조회 직후 결제 완료 → 주문 `expired`, 결제 `succeeded`, 활성 구매 권한 1개.
  - 결제 실패 조회 직후 성공 처리 → 주문 `paid`, 결제 `failed`, 활성 구매 권한 1개.
- **영향:** 구매자 주문 내역, 콘텐츠 권한, 매출·정산 집계가 서로 다른 상태를 표시할 수 있습니다.
- **권장:** 조건부 UPDATE와 영향받은 행 수 검사, 일관된 잠금 순서와 트랜잭션을 적용합니다. 한 주문에 여러 결제 시도가 생기는 경우까지 포함해 상태 전이 규칙을 정리합니다.

### 3) P1 — 한 번만 사용 가능한 쿠폰이 동시 주문에 중복 적용됨

- **근거:** [commerce.ts:39](E:/프로젝트/링고/lib/server/commerce.ts:39), [commerce.ts:114](E:/프로젝트/링고/lib/server/commerce.ts:114), [commerce.ts:134](E:/프로젝트/링고/lib/server/commerce.ts:134)
- 쿠폰 사용 가능 횟수 조회와 주문 생성이 하나의 원자적 작업이 아닙니다.
- **재현:** 전체 사용 한도 1회·1인 한도 1회 쿠폰으로 동일 구매자가 주문 두 건을 동시에 생성했습니다. **두 건 모두 성공했고 각각 1,000센트가 할인**됐습니다.
- **영향:** 쿠폰 비용과 사용 한도를 초과할 수 있습니다.
- **권장:** 쿠폰 사용 예약과 주문 생성을 같은 트랜잭션에서 직렬화하고, 예약 만료·주문 취소·환불 시 사용량 복구까지 함께 검증합니다.

### 4) P1 — 취소 뒤 늦게 들어온 결제를 관리자도 정상 환불 처리할 수 없음

- **근거:** [commerce.ts:232](E:/프로젝트/링고/lib/server/commerce.ts:232), [commerce.ts:413](E:/프로젝트/링고/lib/server/commerce.ts:413)
- 늦은 결제는 결제 상태만 성공으로 기록하고 주문 상태는 취소/만료로 유지합니다. 기록에는 수동 환불을 안내하지만, 환불 함수는 `paid` 주문만 허용합니다.
- **재현:** 주문 취소 → 결제 성공 콜백 → 관리자 수동 환불 요청. 주문은 `cancelled`, 결제는 `succeeded`, 구매 권한은 0개였으며 수동 환불도 `invalid_state`로 거절됐습니다.
- **영향:** 돈이 들어왔는데 콘텐츠를 받지 못한 고객을 기존 환불 화면으로 처리하기 어렵습니다.
- **권장:** 주문 상태와 별개로 실제 수납된 결제 건을 환불·대사할 수 있는 예외 처리 목록과 작업 경로를 만듭니다.

### 5) P1 — 웹훅에서 결제사·실제 금액·통화를 대조하지 않음

- **근거:** [gateway-provider.ts:31](E:/프로젝트/링고/lib/server/payments/gateway-provider.ts:31), [webhook route.ts:36](<E:/프로젝트/링고/app/api/payments/webhook/[provider]/route.ts:36>)
- 서명은 검사하지만, 이벤트가 가리키는 결제의 provider와 URL의 provider가 같은지 확인하지 않습니다. 이벤트의 실제 결제 금액·통화도 정규화하여 대조하지 않습니다. `confirmPayment`의 금액 검사는 내부 DB의 결제 금액과 주문 금액 사이 검사입니다.
- **재현:** 테스트 서명으로 PearPay 웹훅 처리기를 호출하면서 NextPay 결제 ID, 금액 1, 통화 KRW를 넣었습니다. 내부 주문은 10,000센트 USD인데 **HTTP 200과 결제 완료·권한 발급**이 이루어졌습니다.
- **범위:** 실제 PG 이벤트나 외부 공격을 사용한 것이 아닙니다. 현재 PG 어댑터는 미구현 상태이므로 **실제 연동을 완성하기 전에 수정할 계약 검증 문제**입니다.
- **권장:** 공식 PG 명세에 맞춰 금액·통화·가맹점·결제사·참조 ID를 검증합니다. `refunded` 이벤트도 현재 적용 분기가 없으므로 별도 대사/환불 상태 반영이 필요합니다.

### 6) P2 — 실제 콘텐츠가 없는 강의도 판매 상태 유지 가능

- **근거:** [catalog.ts:200](E:/프로젝트/링고/lib/server/catalog.ts:200)
- 강의 납품 가능 여부는 `lessons.length > 0`만 확인합니다. 각 강의에 영상, 노트, 실제 소속 파일이 있는지는 검증하지 않습니다.
- **재현:** 판매 중인 강의를 제목만 있는 항목으로 수정했습니다. `body`, `assetId`, `videoUrl`가 모두 `null`인데 `published` 상태가 유지됐습니다.
- **영향:** 구매자는 결제 후 ‘콘텐츠 준비 중’인 빈 강의만 볼 수 있습니다.
- **권장:** 판매/심사 시 실제 이용 가능한 콘텐츠를 검사하고, 예약 판매를 지원하려면 공개 예정일과 제공 범위를 별도 상품 정책으로 표시합니다.

### 7) P2 — 강의 순서를 바꾸면 수강 완료 표시가 다른 강의에 붙음

- **근거:** [schema.ts:385](E:/프로젝트/링고/db/schema.ts:385), [product-form.tsx:73](E:/프로젝트/링고/components/console/product-form.tsx:73), [account/actions.ts:30](<E:/프로젝트/링고/app/(site)/account/actions.ts:30>)
- 진도를 영구적인 강의 ID가 아닌 배열 순번으로 저장합니다. 판매자는 그 배열을 재정렬·삭제할 수 있습니다.
- **재현:** A, B 중 A를 완료 처리한 뒤 B, A로 순서를 변경했습니다. 완료한 강의가 **A에서 B로 표시**됐습니다.
- **권장:** 각 강의에 유지되는 ID를 두고 진도를 연결합니다. 기존 순번 기반 데이터의 이전 방안과 삭제된 강의 처리도 필요합니다.

### 8) P2 — 잘못된 페이지 번호가 홈 전체의 서버 오류로 이어짐

- **근거:** [home page.tsx:56](<E:/프로젝트/링고/app/(site)/page.tsx:56>), [list.ts:10](E:/프로젝트/링고/lib/server/list.ts:10)
- `Math.max(1, Number(...))`는 `Infinity`와 지나치게 큰 수, 소수에 대한 안전한 페이지 번호 검증이 아닙니다.
- **재현:** `GET /?page=Infinity` → **HTTP 500**, DB 오류 `invalid input syntax for type bigint: "Infinity"`.
- **영향:** 잘못 만들어진 링크를 열면 안내 화면 대신 전체 페이지가 실패합니다.
- **권장:** 유한한 안전 정수와 상한을 검증하고, 잘못된 값은 첫 페이지로 정규화하거나 명확한 오류 응답을 반환합니다. 공통 목록 파서도 함께 수정합니다.

## 3. UI·UX 평가

**좋은 점:** 크림색·코럴색의 브랜드 톤, 홈 배너와 상품 카드의 계층, 관리자/판매자 업무 묶음이 일관됩니다. 한국어 배너는 기울임 없는 글자로 표시됩니다. 판매자 콘솔의 ‘메인으로’·프로필은 PC와 모바일 모두 사이드바 하단에 표시되며 메뉴 영역과 분리되어 있습니다. 메뉴 검색, 상품 등록의 임시저장 → 파일 첨부 → 심사 안내, 빈 목록 안내, 서버 권한 검사와 중복 클릭 비활성화도 갖춰져 있습니다. 확인한 모바일 홈·판매자 상품 등록에서는 페이지 전체의 가로 넘침을 발견하지 못했습니다.

### 9) P2 — 모바일 콘솔 메뉴의 키보드 접근성 보완 필요

- **근거:** [shell.tsx:95](E:/프로젝트/링고/components/console/shell.tsx:95), [console.css:46](E:/프로젝트/링고/app/console.css:46)
- **브라우저 재현:** 메뉴를 열어도 포커스가 배경의 ‘메뉴 열기’에 남았습니다. Tab을 누르면 메뉴 내부가 아닌 배경 상단 로고로 이동했습니다. Esc 이후에도 `rc-sidebar open` 상태가 유지됐습니다.
- 모바일 메뉴가 모달처럼 배경을 덮지만 포커스 이동/복귀, 포커스 제한, 배경 비활성화, Esc 닫기가 구현되어 있지 않습니다. 닫힌 메뉴도 transform으로만 화면 밖에 배치합니다.
- **권장:** 검증된 Drawer/Dialog 컴포넌트를 적용하거나 동등한 키보드·스크린리더 동작을 구현합니다.

## 4. 정상 동작을 확인한 부분

- 정상 결제 후 구매 권한이 1개 발급됐고, 동일 결제 ID의 성공 처리를 반복해도 중복 발급되지 않았습니다.
- 다른 구매자는 해당 주문의 관리용 조회를 할 수 없었습니다(`not_found`).
- 정산 대기 중인 주문 환불 시 비어진 정산서가 취소되고 금액이 0으로 정리됐습니다.
- 지급 완료로 기록한 정산의 주문을 환불하면 다음 정산에서 차감할 음수 조정액이 생성됐습니다. 9,000센트 정산액에 대해 -9,000센트가 기록됐습니다.
- 비로그인 `/admin`, `/seller`는 로그인으로 307 이동하며, 복귀 경로가 유지됐습니다.
- 비로그인 비공개 파일 다운로드는 401, `/media/private/...`는 404였습니다.
- 로컬 홈의 OG 메타데이터는 현재 접속 호스트의 `/api/share-card`를 사용했습니다. Kakao 크롤러 User-Agent로 해당 이미지를 요청해 **200, image/png, 1200×630, 113,328바이트**를 확인했습니다. 이는 로컬 HTTP 검증이며 실제 카카오톡 앱 공유 완료를 뜻하지 않습니다.
- 확인한 홈·판매자 화면에서 기존 `user-select` hydration 오류는 재현되지 않았습니다. 사용자 Chrome의 확장 프로그램 조합 전체를 검증한 것은 아닙니다.

**별도 관찰:** 구매자 로그인 화면을 거치는 동안 개발 모드에서 `Failed to execute 'measure' on 'Performance': 'LoginPage' cannot have a negative time stamp` 오류가 1회 나타났습니다. 스택은 React Server DOM/Turbopack의 성능 측정 코드였고, 구매자 로그인은 완료됐습니다. 계정 화면 새로고침 후 오류 배지는 사라졌습니다. 기존 hydration 오류와는 다른 현상이며, 운영 빌드 재현 및 정확한 원인을 확인하지 못했으므로 확정된 서비스 로직 결함과 구분합니다.

## 5. 운영 준비와 검증 체계 보완

**실제 결제 연동은 미완성입니다.** [gateway-provider.ts:27](E:/프로젝트/링고/lib/server/payments/gateway-provider.ts:27)의 PearPay/NextPay 결제 생성과 환불은 명시적으로 미구현 오류를 발생시킵니다. 환경변수만 설정한다고 실제 결제가 완성되지 않습니다. 계약한 PG의 공식 명세를 기준으로 결제·취소·환불·서명·중복 이벤트·금액 대사를 마무리해야 합니다.

관리자 결제 설정 화면에서도 PearPay·NextPay는 ‘사용 불가’, 테스트 결제만 ‘사용중’으로 표시됐습니다. DB는 PGlite, 저장소는 로컬 디스크, SMTP는 ‘미설정 — 기록만 됨’ 상태였습니다. 현재 로컬 환경의 비밀번호 재설정/주문 안내 메일은 실제 수신함으로 발송되지 않습니다.

로컬 `.env.local`에는 특정 과거 Quick Tunnel의 `APP_URL`이 남아 있습니다. 공유 카드에는 현재 요청 호스트를 쓰지만 메일·결제 복귀 URL은 [request.ts:40](E:/프로젝트/링고/lib/server/request.ts:40)의 `APP_URL`을 우선합니다. 새 터널로 테스트할 때 이 값도 맞춰야 합니다. 주소의 현재 외부 도달 여부는 이번 점검에서 확인하지 않았습니다.

현재 로컬 설정은 데모 로그인 활성화 상태이며 최고 관리자 버튼이 표시됩니다. 개발용으로는 의도된 기능이지만, 해당 서버를 터널로 공개하면 비밀번호 없이 관리자 데모 계정에 접근할 수 있다는 특성이 있습니다. 실제 운영 배포에서는 데모 로그인·데모 데이터·테스트 결제를 분리해야 합니다.

기존 테스트 스크립트는 상당수 준비되어 있으나 모두 실행한 것은 아닙니다. 일부 스크립트는 실제 실행 중인 3031 포트를 기본 대상으로 삼고 데이터를 변경하며, [coupon-math.mjs:10](E:/프로젝트/링고/tests/tools/coupon-math.mjs:10) 등에는 Linux Chromium 절대 경로가 남아 있어 현재 Windows 환경에서 그대로 쓰기 어렵습니다. 공통 실행 설정, 독립 테스트 DB 생성, 브라우저 경로의 일관된 설정, CI 연동이 필요합니다. 이번에 찾은 동시성·지연 콜백·강의 재정렬 사례를 회귀 테스트에 포함할 것을 권장합니다.

확장 운영 관점에서 확인할 사항도 있습니다. 로그인 등의 요청 제한은 프로세스 메모리 기반이므로 서버가 여러 대이면 한도를 공유하지 않습니다. 로컬 영상 파일 전송에는 HTTP Range 처리가 없어 대용량 영상의 탐색·재개 품질을 추가 검증해야 합니다. 두 항목 모두 이번에 실운영 장애나 모바일 기기별 재생 실패를 재현한 것은 아닙니다.
